软件过程

软件开发的基本过程

  • 需求分析：清楚了解客户需求中的产品功能、特性、性能、界面和具体规格等，确定软件产品所能达到的目标。
  • 设计：考虑如何在逻辑、程序上去实现所定义的产品功能、特性等，可分为概要设计和详细设计。
  • 编程：将设计转换成计算机可读的形式。
  • 测试：对设计、编程进行验证和用户需求确认的过程。
  • 维护：维持软件运行，修改软件缺陷、增强已有功能、增加新功能、升级等。

软件开发过程模型

  • 瀑布模型、原型模型、螺旋模型、并发模型、改进的 V 模型、构件组装模型
  • 快速应用开发 (RAD) 模型、Rational 统一过程模型和 UML
  • 敏捷方法—极限编程模型、增量模型和迭代模型

敏捷方法之极限编程 (XP)

极限编程理念

理念 内容
个体和交互 胜过过程和工具
可以工作的软件 胜过面面俱到的文档
客户合作 胜过合同谈判
响应变化 胜过遵循计划
  • 格言：“沟通、简化、反馈、勇气”
  • 原则：最优先交付有价值的软件；提倡可持续开发速度；后期仍欢迎需求改变；团队定期反省。
  • 适合场景：小团队 (2-10人)、快速变化或不稳定的需求、“高风险”、强调可测试性。

阶段性开发模型

  • 增量开发：在软件开发生命周期的各个阶段中，逐步增加产品的功能。
  • 迭代开发：在软件开发生命周期的各个阶段中，反复循环地执行各个阶段的活动。

软件缺陷

什么是软件缺陷

  • 从产品内部看，是软件产品开发或维护过程中所存在的错误、毛病等各种问题。
  • 从外部看，是系统所需要实现的某种功能的失效或违背。

软件缺陷表现形式

  • 功能、特性没有实现或部分实现
  • 设计不合理，存在缺陷
  • 实际结果和预期结果不一致
  • 运行出错，包括运行中断、系统崩溃、界面混乱
  • 数据结果不正确、精度不够
  • 用户不能接受的其他问题，如存取时间过长、界面不美观

软件缺陷的产生

  • 项目期限的压力、产品的复杂度、沟通不良
  • 开发人员的疲劳、压力或受到干扰
  • 缺乏足够的知识、技能和经验、不了解客户的需求、缺乏动力
  • 技术问题：算法错误，语法错误，计算和精度问题，接口参数传递不匹配等
  • 团队工作：误解、沟通不充分
  • 软件本身：文档错误、用户使用场合、时间上不协调、或不一致性所带来的问题

软件质量

软件质量需求的背景

  • 质量的需求被绝对认可，但质量在软件业的地位还不是十分坚固
  • 市场力量对软件质量的影响，既有正面的，也有负面的
  • 软件越来越复杂，软件的复杂性是软件质量的另一个敌人
  • 软件缺陷造成的质量事故数不胜数，给企业带来的损失或负面影响很大

软件质量需求的内容

  • 用户的需求：功能强大且界面美观易用；内容健康；数据安全、受保护和兼容；及时得到新的产品或服务；可靠性很高。
  • 软件企业的需求：市场竞争的需要；降低“质量问题产生的成本”，增加盈利；进入国际市场的关键门坎；容易维护、移植和扩充。

软件质量的定义

ANSI/IEEE STD729 定义：软件产品满足规定的和隐含的与需求能力有关的全部特征和特性。

  • 软件产品质量满足用户要求的程度
  • 软件各种属性的组合程度
  • 用户对软件产品的综合反映程度
  • 软件在使用过程中满足用户要求的程度

包含三个方面：

  • 软件产品的质量：满足使用要求的程度
  • 软件开发过程的质量：能否满足开发所带来的成本、时间和风险等要求
  • 软件在其商业环境中所表现的质量

软件质量的特性

3A特性

  • Accountability (可说明性)：用户可以基于产品或服务的描述和定义进行使用
  • Availability (有效性)：产品或服务对于绝大多数客户总是有效的
  • Accessibility (易用性)：对于用户，产品或服务非常容易使用并且一定是非常有用的功能

3维特性

  • 功能性 (Functionality)：按照既定意图和要求，执行指定用例的能力
  • 可靠性 (Reliability)：软件坚固性和可靠性、资源利用率、代码完整性以及技术兼容性等
  • 性能 (Performance)：衡量系统占用系统资源 (CPU时间、内存) 和系统响应、表现的状态

ISO 9126 定义特性

  • 功能：与一组功能及其指定性质有关的一组属性
  • 可靠：在规定的一段时间和条件下，与软件维持其性能水平的能力有关的一组属性
  • 易用：由一组规定或潜在的用户为使用软件所需作的努力和所作的评价有关的一组属性
  • 效率：与在规定条件下软件的性能水平与所使用资源量之间关系有关的一组属性
  • 可维护：与进行指定的修改所需的努力有关的一组属性
  • 可移植：与软件从一个环境转移到另一个环境的能力有关的一组属性

软件质量含义分析

SEI 的 Watts Humphrey 认为软件质量是“在实用性、需求、可靠性和可维护性等方面，达到优秀的水准”

  • 客户满意度：使最终的软件产品能最大限度地满足客户需求的程度
  • 一致性准则：在生命周期的每个阶段中，其工作产品总能保持与上一阶段工作产品的一致性
  • 软件质量度量：设立软件质量度量指标体系，并以此来度量软件产品的质量
  • 过程质量观：软件系统的质量取决于开发和维护它的过程的质量

优质软件应该：相对的无产品缺陷或只有极少量的缺陷；能够准时递交给用户并且所用的费用都是在预算内的并且满足客户需求；可维护的；最终评价依赖于用户的反馈。

软件质量的内容

软件质量由三部分构成：

  1. 软件产品质量：满足使用要求的程度（功能性、可用性、可靠性、性能、容量、可测量性、可维护性、兼容性、可扩展性等）
  2. 软件开发过程质量：能否满足开发所带来的成本、时间和风险等要求（CMM、PSP/TSP、ISO 9000、SPICE）
  3. 软件商业环境质量：在生存的商业环境中体现出好坏，不一定与产品质量以及软件开发过程质量保持同步

软件质量工程体系

概述

系统工程学的思想

  • 研究多个子系统构成的整体系统所具有的多种不同目标的相互协调，以期系统功能的最优化、最大限度地发挥系统组成部分的能力。
  • 系统分析过程的逻辑结构：明确问题、确定目标、系统综合、系统分析、系统选择、决策、实施计划等环节。

软件质量工程体系的建立

建立和实施质量管理体系的方法：

  1. 确定顾客和其他相关方的需求和期望
  2. 建立组织的质量方针和质量目标
  3. 确定实现质量目标必需的过程和职责
  4. 确定和提供实现质量目标必需的资源
  5. 规定测量每个过程的有效性和效率的方法
  6. 应用这些测量方法确定每个过程的有效性和效率
  7. 确定防止不合格并消除产生原因的措施
  8. 建立和应用持续改进质量管理体系的过程

要将软件质量管理作为一个系统来管理，运用系统科学的方法，通过有关质量的各种信息反馈与调控，对软件质量进行全面、综合的系统性管理。

软件质量工程体系的构成

  • 软件质量计划
  • 软件质量组织
  • 软件质量活动（质量控制、质量保证、质量改进）
  • 软件质量成本
  • 软件质量度量

软件质量因素和指标

软件质量指标（6个品质要素）

品质要素 定义
正确性 实现的功能达到设计规范，并满足用户需求的程度
可靠性 规定的时间和条件下，仍能维持其性能水准的程度
易用性 用户掌握软件操作所要付出的时间及努力程度
效率 软件执行某项功能所需电脑资源（含时间）的有效程度
可维护性 当环境改变或软件发生错误时，执行修改或恢复所做努力的程度
可移植性 从一个系统/环境移到另一系统/环境的容易程度

质量指标：衡量那些可识别的软件质量特性的项目，有助于软件质量进行度量，利用软件工程方法来达到特定的质量目标。

功能性的质量指标：功能的正确性、准确性、完整性
可用性的质量指标：可操作性、通用性、一致性
可靠性的质量指标：系统自我恢复能力、健壮性、系统的分布性
性能的质量指标：有效性、安全管理/完整性、易存取性
可维护性的质量指标：简单性、自我描述性、系统兼容性、文档质量、增强能力/灵活性、模块化、可测试性、可追溯性
可移植性的质量指标：独立性、可重用性、互操作性、虚拟性、一般性

软件质量因素

  • 软件产品的质量因素（产品修改、产品移植、产品运行）
  • 软件过程的质量因素（项目计划过程、项目设计过程、项目实施过程、软件维护过程、软件商业环境过程）

软件质量模型分析

软件质量模型

  • McCall 软件质量模型 (GE模型, 1977)：11个指标，分为产品操作、产品修订和产品转移
  • Boehm 模型 (1978)：基于很多特性和标准
  • ISO 简化的软件质量模型：6个质量目标，每个质量目标有很多属性

ISO 三层模型

  • 高层：软件质量需求评价准则 (SQRC)
  • 中层：软件质量设计评价准则 (SQDC)
  • 低层：软件质量度量评价准则 (SQMC)

模型评价和分析

  • 存在差别：定义不完全一致
  • 思想接近：总体上表达的思想非常接近
  • 目的相同：软件质量因素、准则和度量三者综合的软件质量结构模型

软件质量工作层次

  • 软件质量方针：由组织的最高管理者正式发布的，该组织的质量宗旨、目标和质量方向，并形成文件。
  • 软件质量控制：设定标准、测量结果，判定是否达到预期要求，对质量问题采取措施进行补救并防止再发生的过程。
  • 软件质量保证：为保护产品和服务充分满足消费者要求的质量而进行的有计划有组织的活动，致力于提供对满足质量要求的信任。
  • 软件质量管理：在质量方针指导下，指挥和控制组织的质量活动，协调质量的各项工作。
  • 软件质量改进：致力于增强满足质量要求的能力，是一个持续过程。常用模型：IDEAL、六西格玛、PDCA、PEIS、CMM、SPICE等。

软件质量成本

质量成本概念

质量成本 = 保证成本 + 损失成本

  • 保证成本 = 预防成本 + 评价成本
  • 预防成本：预防产生质量问题的费用
  • 评价成本：为评定软件产品或服务是否符合质量要求而进行的试验、测试等支出
  • 损失成本：分为内部损失成本（发布前发现质量问题）和外部损失成本（发布后因质量问题产生的损失）

引入质量成本的意义

将质量与企业经济效益直接联系起来，使质量得以用货币语言表达，让管理层更容易树立质量至上的理念。

软件的劣质成本

  • PONC (Price of Nonconformance)：“不符合要求的代价”，即劣质成本
  • COPQ (Cost of Poor Quality)：“不良成本”，即劣质成本
  • 分类：故障成本、过程成本、损失成本
  • 软件劣质成本高达 46%-80%

软件质量标准和度量

软件质量标准体系介绍

  • 标准体系空间：纵向分为产品和过程质量管理标准，横向分为通用和各个行业的质量标准
  • 标准体系层次：原理标准、要素标准、指南和补充
  • 示例：ISO/IEC 9126 (产品质量)、ISO/IEC 12207 (软件过程)、ISO/IEC 14598 (软件产品评价) 等

软件质量度量的地位

  • 项目质量度量：度量项目特征和项目执行的质量状态
  • 产品质量度量：度量软件产品的特性和质量属性
  • 过程质量度量：度量软件开发和维护的改进过程

软件质量度量

测量基础

测量原理

  • 测量：对产品过程的某个属性的范围、数量、维度、容量或大小提供一个定量的指示。
  • 度量：对软件产品进行范围广泛的测度，给出一个系统、构件或过程的某个给定属性的度的定量测量。
  • 指标：一个度量或一组度量的组合，对软件过程、项目或产品质量提供更全面、深入的评价和了解。

度量尺度

  • 分类尺度：分成一系列类别（如功能性、可靠性等）
  • 序列尺度：分类并排序（如满意度等级）
  • 间隔尺度：用数值表示差异，但无绝对零值
  • 比值尺度：有绝对零值

测量标准

  • 有效性：测量结果正确反映被测试对象的实际状况和程度
  • 可靠性：使用同样的测量方法对同样的事物进行多次测量，得到值的一致性

测量过程和原则

  • 基本原则：基于正确理论；定义具有一致性、客观性、无二义性；有经验和直觉说服力；简单可计算；剪裁适应特定产品和过程；自动化；正确统计技术；可靠；建立反馈机制。

软件开发生命周期的度量活动

  • 软件项目质量度量：描述项目特性和执行状态（计划有效性、资源使用效率、成本效益、风险、进度、生产力等）
  • 软件产品质量度量：描述软件产品特征（规模大小、复杂度、设计特征、性能、质量水平等）
  • 软件过程质量度量：用于软件开发、维护过程的优化和改进（缺陷移除效率、缺陷到达模式、修复效率等）

软件项目的质量度量

度量分类

  • 进度度量：通过任务分解、工作量度量、有效资源分配等做出计划，将实际结果和计划值对比
  • 风险度量：通过“风险发生的概率”和“风险发生后所带来的损失”来评估
  • 规模度量：以代码行数、功能点数、对象点或特征点等衡量，是工作量度量、进度度量的基础
  • 复杂度度量：确定程序控制流或软件系统结构的复杂程度
  • 缺陷度量：帮助确定产品缺陷分布、变化状态，分析修复工作量、设计弱点、预测发布时间和遗留缺陷
  • 工作量度量：任务分解并结合人力资源水平来度量
  • 其他：顾客满意度、需求稳定性、资源利用效率、文档复审水平、问题解决能力、代码动态增长等

规模度量

  • 德尔菲法：专家评估技术
  • 构造性成本模型 (COCOMO)
  • 代码行度量、功能点分析、对象点方法

顾客满意度度量

要素 内容
软件产品 功能性、可靠性、易用性、效率性、可维护性、可移植性

软件产品的质量度量

度量分类

  • 直接度量：软件缺陷数、缺陷密度、软件性能、所耗资源、投入成本等
  • 间接度量：复杂性、客户满意度、功能性、效率、可维护性等

软件缺陷的度量

  • 缺陷密度：软件缺陷在规模上的分布（如每KLOC缺陷数）
  • 缺陷率：缺陷在时间上的分布
  • 整体缺陷清除率：开发过程中发现的所有缺陷数 / 发现的总缺陷数
  • 阶段性缺陷清除率：开发阶段清除的缺陷数 / 产品中潜伏的缺陷数

软件复杂性的度量

  • McCabe 环形复杂度：( V(G) = E - N + 2 )（E为边数，N为结点数），也可用区域数D表示。优点：指出复杂模块、度量测试计划、与语言无关。缺点：局限于二元决策。建议圈复杂度不超过10。
  • 语法构造方法：根据操作符和操作数的数量计算复杂性。
  • 结构度量方法：如 Henry 模型 ( Cp = (扇入 \times 扇出)^2 )，Card/Glass 模型 ( Ct = St + Dt )。

顾客满意度度量（产品层面）

要素 内容
技术 质量、可靠性、有效性、易用性、价格、安装、新技术支持与维护
市场营销 解决方案、接触点、信息管理
购买流程 请求手续、保证期限、注意事项
交付 准时、准确、交付后过程
企业形象 技术领导、财务稳定性、执行印象

共性过程质量要素

  • 进度（里程碑有效性 ME，迭代效率 IE）
  • 资源和费用（人员稳定性 PSI，成本性能指数 CPI，资源完备性 RE）
  • 评审（评审效率 CE，评审人力率 CF）
  • 缺陷（阶段缺陷清除率 DRE，缺陷密度 BD）

  • 技术完备性（计算机资源利用率 SC，技术性能 TE，模块复用率 ME）
  • 需求稳定性（需求稳定性 RSI）

个性过程质量要素（按阶段）

  • 需求规格说明书：需求的确认度 Q0，需求的无二义性 Q1，设计的兼容性 DE
  • 代码审查：审查效率 WE
  • 测试用例和环境：测试用例的深度 TCD，测试用例的质量 TCQ，测试环境的稳定性 TSI
  • 问题和缺陷修复：修复响应时间 RRT，积压管理指标 BMI，拖欠修复百分数 DRE，修复质量 RQ

统计分析步骤

  1. 收集和分类软件缺陷信息
  2. 找出导致每个缺陷的原因
  3. 使用 Pareto 规则 (80/20 法则) 分离主要因素
  4. 纠正引起缺陷的问题

错误的根本原因来源

  • 说明不完整或错误 (IES)
  • 与客户交流不够所产生的误解 (MCC)
  • 故意与说明偏离 (IDS)
  • 违反编程标准 (VPS)
  • 数据表示有错 (EDR)
  • 模块接口不一致 (IMI)
  • 设计逻辑有错 (EDL)
  • 不完整或错误的测试 (IET)
  • 不准确或不完整的文档 (IID)
  • 将设计翻译成程序设计语言中的错误 (PLT)
  • 不清晰或不一致的人机界面 (HCI)

软件质量标准

软件质量标准概述

标准的层次

  • 国际标准 (ISO)
  • 国家标准 (GB, ANSI, BS, JIS)
  • 行业标准 (IEEE, GJB, DOD-STD, MIL-S)
  • 企业规范 (如 IBM 程序设计开发指南)
  • 项目规范

常用标准简介

  • ISO 9001-3：ISO 9001 在软件行业的应用指南，因软件没有明显的生产阶段，设计阶段质量活动尤为重要。
  • ISO 9001-3 与 CMM：都以全面质量管理为理论基础，但设计思路不同。ISO 9000-3 是软件组织的实施指南，CMM 专门针对软件设计行业。
  • 从 CMM 到 CMMI：CMMI 是 SW-CMM 的修订本，兼收了更合理、更科学和更周密的优点。
  • CMMI 与 TR 15504：ISO/IEC TR 15504《软件过程评估》受 CMM 启发，是软件过程评估的国际标准。
  • IEEE 软件工程标准：包括 IEEE 730 (结构与内容)、IEEE/EIA Std 12207 (软件生命周期过程)、IEEE Std 1012 (验证与确认)、IEEE Std 1028 (评审) 等。
  • Tick IT：鼓励软件开发商和采购商考虑质量真正含义，提供管理软件开发质量的实用结构。

能力成熟度模型 CMMI

CMMI 质量思想

软件过程能力成熟度是指一个特定过程被明确地定义、管理、测量、控制并且是有效的程度。成熟度意味着能力上的增长。

成熟等级：

  1. 初始级：基本上没有健全的软件工程管理制度。
  2. 可重复级：有基本的软件项目管理行为，基于相似产品中的经验。
  3. 已定义级：已为软件生产的过程编制了完整的文档，软件过程的管理方面和技术方面都明确做了定义。
  4. 已管理级：对每个项目都设定质量和生产目标，并不断测量，偏离时采取行动修正。
  5. 优化级：目标是连续地改进软件过程，使用统计质量和过程控制技术作为指导。

CMMI 关键过程域 (KPA)

每一级（除第一级外）包含了若干关键过程域 (KPA)，指出了企业需要集中力量改进的软件过程，每个 KPA 包含一个或多个目标，以及一组关键实践活动。

CMMI 内容分级

  • “必需的”级别：目标，是过程改进的基础。
  • “期望的”级别：方法，是达到目标的实践手段。
  • “提供信息的”级别：目的、介绍性说明、引用、注释、典型工作产品、子实践、学科扩充等。

CMMI 流程改进

三大步：

  1. 确定流程改进的总体框架（总体方案、策略、目标、度量体系等）。
  2. 细化框架内的要求（详细过程定义、角色、入口/出口准则、输入/输出、过程步骤、度量方法等）。
  3. 明确流程改进的度量方法与标准。

CMMI 量化管理

CMMI 第四级（已管理级）组织根据缺陷数据建立软件过程能力基线（包括期望 MEAN，能力上限 UCL，能力下限 LCL），用于帮助未来项目设立量化质量目标，理解和控制实际结果。

CMMI 质量框架意义

CMMI 不仅指导过程改进，而且将全面质量管理概念应用到软件上，从需求管理到项目计划、控制、获取、质量保证、配置管理，实现全面质量管理。

软件评审

为什么需要评审

  • 从成本上衡量：缺陷发现得越晚纠正费用越高。前一阶段的错误会导致后一阶段的工作结果中有相应的错误，且错误逐渐累积。
  • 从技术上衡量：早期发现缺陷，减少后期返工。
  • 从效率上衡量：
    • 开发工程师：减少修订缺陷时间，提高编程效率，减少测试调试时间。
    • 项目负责人：缩短开发周期，减少维护费用，控制项目风险和质量。
    • 测试工程师：更多精力放到测试用例设计上，提高测试效率。
    • 维护人员：维护工作减少，产品可维护性增强。

评审的内容

  • 管理评审：由最高管理者发起，评审管理体系（适宜性、有效性、充分性）。包括质量体系总体评价、改进措施、资源需求等。
  • 技术评审：对产品及各个阶段输出内容进行评估，确保需求说明、设计说明书与最初说明书保持一致。
  • 文档评审：包括需求评审（市场需求说明书、产品需求说明书、功能说明书等）、设计评审（总体设计说明书、详细设计说明书）、代码评审、质量验证评审（测试计划、测试用例等）。检查列表：正确性、完整性、一致性、有效性、易测性、模块化、清晰性、可行性、可靠性、可追溯性。
  • 过程评审：对软件开发过程的评审，保证 SQA 组织定义的软件过程在项目中得到遵守。目的：评估质量保证流程，处理不符合问题，总结好的经验，指出需要完善的地方。

评审的方法和技术

评审的方法（由非正式到正式）

  • 临时评审 (Ad hoc review)
  • 轮查 (Pass-round)
  • 走查 (Walkthrough)
  • 小组评审 (Group Review)
  • 审查 (Inspection)

选择标准：对最可能产生风险的工作成果采用最正式的评审方法（核心代码用审查，一般代码用临时评审）。

评审的技术

  • 缺陷检查表：列出容易出现的典型错误。
  • 规则集：业界通用规范或企业自定义规则。
  • 评审工具：如 NASA 的 ARM（自动需求度量）。
  • 从不同角色理解：不同角色对产品/文档的理解不同。
  • 场景：按照用户使用场景进行评审。

评审会议

准备评审会议

  1. 制定评审计划和评审时间
  2. 组建评审组（评审组长和成员）
  3. 准备评审材料（基础文档、重大决策文档、挑战性模块、可复用部件）
  4. 发送审查包（被审查产品、前期文档、相关标准、表格、检查表、测试文档等）
  5. 制定活动进程表（安排房间、日期、次数，通知评审组成员）

召开评审会议

  1. 由评审员/作者进行演示或说明
  2. 评审员就不清楚或疑惑的地方与作者沟通
  3. 记录员完成会议记录（清楚、简明，缺陷分类）

评审结果

  • 接受：不存在大的缺陷，通过
  • 有条件接受：存在一些小缺陷，修订后通过
  • 不能接受：有较多缺陷，需修改后重新评审
  • 评审未完成：因故未能完成，需要后续会议

评审中的注意事项

  • 人身攻击：矛盾集中于评审内容本身
  • 无休止的争论：记录问题，留给作者决定
  • 偏离会议中心：及时拉回主题
  • 鼓励所有人发言：按座位顺序轮流发表意见

评审结果的跟踪

  • 评审结果为有条件接受或不能接受时，需跟踪修正情况。
  • 评审结果分析：有效性和效率、成本。

如何实施成功的评审

解决不成功评审的主观因素

  • 对所有工程师进行评审培训
  • 预防个人冲突，避免对作者有人身攻击的工程师加入评审小组
  • 将评审活动加入项目计划，分配足够资源
  • 收集以前评审数据，了解最有效的评审方法
  • 将评审列入个人时间表，确保有充分时间准备

解决不成功评审的客观因素

  • 异步评审（共享文档、邮件评审）
  • 分布式评审（视频会议）

SQA 的组织活动

软件质量管理组织介绍

基本的软件质量组织

  • 软件测试部门：理想开发人员、测试人员比例 1:2
  • 人才库模式 / 项目模式
  • 软件工程过程组 (SEPG)：领导和协调过程改进的小组
  • 软件过程改进网络 (SPIN)：地区性非盈利组织
  • 质量保证协会 (QAI)：提供质量、过程改进方面的培训、咨询、评估、认证等

SQA 组织活动流程

建立 SQA 组织 → 选择 SQA 任务 → 制订/维护 SQA 计划 → 执行 SQA 计划 → 制定/维护 SQA 流程 → 定义 SQA 培训 → 选择 SQA 工具 → 改进项目的 SQA 流程

SQA 组织结构与角色

常用的组织结构模型

  • 独立的 SQA 部门：优点：保护独立性和客观性，有利于资源共享。缺点：难于深入项目，发现问题不能及时解决。
  • 独立的 SQA 工程师（非独立 SQA 小组）：优点：能深入项目，问题及时解决。缺点：SQA 工程师之间缺乏沟通，独立性和客观性不足。
  • 独立的 SQA 工程师（独立的 SQA 小组）：优点：综合上述两种优点，能深入项目又便于经验分享。

角色的分类和职能

  • 非全职的 QA：项目经理、开发工程师、测试工程师兼职完成 SQA 任务。
  • 全职的 QA：
    • SQA 经理：制定 SQA 策略和发展计划，管理资源，审定 SQA 计划，评审 SQA 工作状态，提交跨项目 SQA 计划。
    • SQA 工程师：按 SQA 计划检查产品，执行评审/审核，记录数据和观察，提交不符合报告，完成 SQA 测量和度量，向 SQA 经理报告。

各角色之间的关系

  • SQA 和项目经理：合作关系，帮助项目经理了解过程执行情况和产品质量。
  • SQA 和开发工程师：良好沟通和合作，避免对立。
  • SQA 和测试工程师：SQA 监督流程，测试针对产品本身。
  • SQA 和 SEPG：SEPG 制定和改进流程，SQA 保证流程正确执行。

SQA 组织的目标和责任

责任

  • 不负责生产高质量的软件产品（那是开发组的责任），不负责制定质量计划。
  • 目标：以独立审查方式监控软件生产任务的执行，提供反映产品质量的信息和数据，辅助软件工程组得到高质量的软件产品。
  • 责任：审计软件经理和软件工程组的质量活动，鉴别活动中出现的偏差。

SQA 计划

实施步骤：了解项目需求 → 选择 SQA 任务 → 估计工作量和资源 → 安排任务和日程 → 形成 SQA 计划 → 协商、评审 → 批准 → 执行。

SQA 计划包含内容：目的、参考文件、管理（组织、任务、责任）、文档、标准定义（文档标准、代码标准等）、评审/审核、配置管理、问题报告和处理、工具/技术/方法、代码控制、事故/灾难控制。

SQA 评审和审核

  • 评审 (Review)：过程进行时对过程的检查，确保过程得到遵循。
  • 审核 (Audit)：对软件工作产品的检查，确保开发工作产品中过程得到遵循。
  • 主要的评审和审核：软件需求评审、概要设计评审、详细设计评审、管理评审、软件验证与确认评审、功能审核、物理审核、综合审核。

SQA 评估任务

  • 软件工具评估：评估正在使用和计划使用的软件工具，确保项目组采用合适的技术和工具。
  • 项目设施评估：检查是否为软件开发和支持提供了所需要的设备和空间。

提高软件设计质量

软件设计

软件设计的目标

软件设计是把软件需求转换为软件表示的过程，是将用户需求准确转化为软件系统的唯一途径。

  • 体系结构设计（概要设计）：高层次设计，将软件需求转化为数据结构和软件的系统结构，定义子系统及其接口。
  • 详细设计：对结构表示进行细化，得到详细数据结构和算法，给程序员清晰的规范说明。

软件设计的目标：确保软件在总体结构、外部接口、主要部件功能分配、全局数据结构以及各主要部件之间的接口等方面的合适性、完备性。具备特征：可靠性、性能和安全、可扩展性、可定制性或可移植性、可维护性、可重用性。

软件设计评价标准

质量属性：

  • 运行时间评价：性能、安全性、可用性、功能性、可使用性
  • 维护时间评价：可修改性、可移植性、可复用性、可测试性
  • 体系结构本质质量：概念完整性、正确性、完备性、可构造性

度量方法：面向功能设计的度量（结构图）、面向对象设计的度量（类图）、复杂度、耦合度、内聚性等。

评价工具和技术：软件设计评审、静态分析（故障树分析、自动交叉检查）、模拟与原型。

软件设计原则

基本原则：以质量为目标，越简单越好。
指导思想：降低模块耦合度，提高模块内聚性。
总体原则：用户需求远比技术重要；需求其实很少改变，改变的是对需求的理解；接受变化；不要低估软件规模的需求；在软件设计中没有捷径；任何体系结构都有优缺点；沟通对设计质量同样重要；工具只是手段；理解完整的软件开发过程；常作验证，早作验证。

技术原则：

  • 开闭原则：对扩展开放，对修改关闭。
  • 单一职责原则：一个类只有一个引起它变化的原因。
  • 里氏代换原则：任何基类可以出现的地方，子类一定可以出现。
  • 依赖倒转原则：抽象不应该依赖于细节，细节应当依赖于抽象。要针对接口编程。
  • 接口隔离原则：为不同的客户端提供不同的服务。
  • 合成/聚合复用原则：在一个新的对象里面使用一些已有的对象。
  • 迪米特法则（最少知识原则）：一个对象应当对其他对象有尽可能少的了解。

  • 中间件的多层分布式体系结构：具有表示层、业务逻辑层和数据层三层或多层。设计要点：安全性、稳定性、易维护、快速响应、系统扩展灵活。

函数处理规则

函数参数、返回值和接口规则

  • 参数的书写要完整，不要只写类型不写参数名；无参数用 void 填充
  • 参数命名要恰当，顺序要合理
  • 如果参数是指针且仅做输入用，加 const 防止被修改
  • 如果输入参数以值传递传递对象，宜改用 const & 方式传递，提高效率
  • 参数个数尽量控制在 5 个以内
  • 不要省略返回值的类型
  • 函数名字与返回值类型在语义上不可冲突
  • 不要将正常值和错误标志混在一起返回：正常值用输出参数，错误标志用 return 语句
  • 有时函数不需要返回值，但为了支持链式表达可以附加返回值
  • 如果函数的返回值是一个对象，注意“引用传递”和“值传递”的不同使用
  • 在函数体的“出口处”，对 return 语句的正确性和效率进行检查

文件结构

定义文件的结构

  1. 版权和版本声明
  2. 对头文件的引用
  3. 程序的实现体（包括数据和代码）

头文件的结构

  • 用 #ifndef / #define / #endif 结构防止头文件被重复引用
  • 用 #include <filename.h> 引用标准库头文件
  • 用 #include "filename.h" 引用非标准库头文件
  • 头文件中只存放“声明”而不存放“定义”
  • 尽量不要在头文件中出现 extern int value 这类声明

空行规则

  • 每个类声明、每个函数定义结束之后加空行
  • 逻辑上密切相关的语句之间不加空行，其它地方应加空行分隔

程序的版式

代码行

  • 一行代码只做一件事情（如只定义一个变量或只写一条语句）
  • if、for、while、do 等语句自占一行，执行语句不得紧跟其后，不论执行语句有多少都要加 {}
  • 尽可能在定义变量的同时初始化该变量（就近原则）

对齐

  • 程序的分界符 { 和 } 应独占一行并且位于同一列，与引用它们的语句左对齐
  • { } 之内的代码块在 { 右边数格处左对齐

长行拆分

  • 代码行最大长度宜控制在 70 至 80 个字符以内
  • 长表达式在低优先级操作符处拆分成新行，操作符放在新行之首
  • 应当将修饰符 * 和 & 紧靠变量名（如 int *x, y;）

注释

  • 注释是对代码的“提示”，不可喧宾夺主
  • 如果代码本来就清楚，则不必加注释
  • 边写代码边注释，修改代码同时修改注释，不再有用的注释要删除
  • 注释应当准确、易懂，防止有二义性
  • 尽量避免在注释中使用缩写
  • 注释的位置应与被描述的代码相邻，可放在上方或右方，不可放在下方
  • 当代码比较长，特别是有多重嵌套时，在段落的结束处加注释

类的版式

  • 两种方式：以数据为中心（private 在前）和以行为为中心（public 在前）
  • 建议采用“以行为为中心”的书写方式，首先考虑类应该提供什么样的接口

表达式

  • 如果代码行中的运算符比较多，用括号确定表达式的操作顺序
  • 不要编写太复杂的复合表达式（如 i = a >= b && c < d && c + f <= g + h;）
  • 不要有多用途的复合表达式（如 d = (a = b + c) + r;）
  • 不要把程序中的复合表达式与“真正的数学表达式”混淆（如 if (a < b < c) 不是数学含义）

基本语句

if 语句

  • 布尔变量：不可与 TRUE、FALSE 或 1、0 比较。正确写法：if (flag) 表示真，if (!flag) 表示假。
  • 整型变量：应当用 == 或 != 直接与 0 比较（if (value == 0)）。
  • 浮点变量：不可用 == 或 != 与任何数字比较，应转化为 >= 或 <= 形式，与允许误差 EPSINON 比较。
  • 指针变量：应当用 == 或 != 与 NULL 比较。
  • if/else/return 组合：应写成 if (condition) { return x; } else { return y; } 或 return (condition ? x : y);。

循环控制变量

  • 不可在 for 循环体内修改循环变量
  • 建议 for 循环控制变量的取值采用“半开半闭区间”写法：for (int x=0; x<N; x++)

内存管理

内存分配方式

  • 静态存储区域：全局变量、static 变量，编译时分配，程序运行期间存在。
  • 栈上：函数内局部变量，函数结束时自动释放，效率高但容量有限。
  • 堆上（动态内存分配）：用 malloc/new 申请，用 free/delete 释放，灵活但问题最多。

常见的内存错误及其对策

  1. 内存分配未成功，却使用了它：使用前检查指针是否为 NULL，用 assert(p!=NULL) 或 if(p==NULL) 防错。
  2. 内存分配成功，但尚未初始化就引用它：无论何种方式创建数组，都别忘了赋初值。
  3. 内存分配成功并且已经初始化，但操作越过了内存边界：注意数组下标“多1”或“少1”的操作。
  4. 忘记了释放内存，造成内存泄漏：malloc/free、new/delete 必须配对使用。
  5. 释放了内存却继续使用它：return 语句不要返回指向“栈内存”的指针或引用；释放内存后将指针设置为 NULL，防止产生“野指针”。

free 和 delete 的正确理解

  • free 和 delete 只是释放指针所指的内存，并没有把指针本身干掉，指针地址仍然不变，但该地址对应的内存是垃圾，成了“野指针”。
  • 指针消亡了并不表示它所指的内存会被自动释放。
  • 内存被释放了并不表示指针会消亡或成为 NULL 指针。

杜绝“野指针”

  • “野指针”不是 NULL 指针，是指向“垃圾”内存的指针，if 语句对它不起作用。
  • 成因：指针变量没有被初始化（刚创建时不会自动成为 NULL，缺省值是随机的）；指针被 free 或 delete 后没有置为 NULL。

其它编程经验

const 的使用

  • const 可以修饰函数的参数、返回值、函数体定义，被 const 修饰的东西都受到强制保护。
  • 用 const 修饰函数的参数：如果参数作输出用，不能用 const；如果输入参数采用“指针传递”，加 const 可防止意外改动；对于非内部数据类型参数，用 void Func(const A &a) 代替 void Func(A a) 可提高效率。
  • 如果函数本来不需要返回值，但为了增加灵活性可以附加返回值。

Java 编程规则

  • 类名首字母大写，字段、方法及对象首字母小写，Java 包全部小写。
  • 自己创建的每一个类都考虑置入一个 main() 用于测试。
  • 将方法设计成简要的、功能性单元。
  • 使类尽可能短小精悍，只解决一个特定的问题。
  • 让一切东西都尽可能地“私有”（private）。
  • 谨慎“巨大对象综合症”。
  • 若不得已进行一些不太雅观的编程，至少把那些代码置于一个类的内部。
  • 考虑使用内部类改善编码及维护。
  • 尽可能细致地加上注释，并用 javadoc 生成文档。
  • 避免使用“魔术数字”，应创建常数并赋予有说服力的名称。
  • 在构建器内部，只进行将对象设为正确状态所需的工作。
  • 若一个对象必须清除，采用 try-finally 方式。
  • 在现成类的基础上创建新类时，首先选择“新建”或“创作”。
  • 用继承及方法覆盖表示行为差异，用字段表示状态差异。
  • 保证每个名字仅对应一个类。
  • 警惕“分析瘫痪”和“过早优化”。
  • 记住注释、细致解释和示例往往具有不可估量的价值。

  • 将数据成员设为私有的，无行为的聚集(C语言形式的struct)除外（第41条）
  • 不要公开内部数据（第42条）
  • 明智地使用 Pimpl（第43条）
  • 优先编写非成员非友元函数（第44条）
  • 总是一起提供 new 和 delete（第45条）
  • 如果提供类专门的 new，应该提供所有标准形式（普通、就地和不抛出）（第46条）
  • 以同样的顺序定义和初始化成员变量（第47条）
  • 在构造函数中用初始化代替赋值（第48条）
  • 避免在构造函数和析构函数中调用虚拟函数（第49条）
  • 将基类析构函数设为公用且虚拟的，或者保护且非虚拟的（第50条）
  • 析构函数、释放和交换绝对不能失败（第51条）
  • 一致地进行复制和销毁（第52条）
  • 显式地启用或者禁止复制（第53条）
  • 避免切片，在基类中考虑用克隆代替复制（第54条）
  • 使用赋值的标准形式（第55条）
  • 只要可行，就提供不会失败的 swap（而且要正确地提供）（第56条）
  • 将类型及其非成员函数接口置于同一名字空间中（第57条）
  • 应该将类型和函数分别置于不同的名字空间中，除非有意想让它们一起工作（第58条）
  • 不要在头文件中或者 #include 之前编写名字空间 using（第59条）

  • 在模块的接口中使用具有良好可移植性的类型（第63条）
  • 理智地结合静态多态性和动态多态性（第64条）
  • 有意地进行显式自定义（第65条）
  • 不要特化函数模板（第66条）
  • 不要无意地编写不通用的代码（第67条）
  • 广泛地使用断言记录内部假设和不变式（第68条）

  • 通过值抛出，通过引用捕获（第73条）
  • 正确地报告、处理和转换错误（第74条）
  • 避免使用异常规范（第75条）
  • 默认时使用 vector，否则选择其他合适的容器（第76条）
  • 用 vector 和 string 代替数组（第77条）
  • 使用 vector（和 string::c_str）与非 C++ API 交换数据（第78条）
  • 在容器中只存储值和智能指针（第79条）
  • 用 push_back 代替其他扩展序列的方式（第80条）
  • 多用范围操作，少用单元素操作（第81条）

  • 使用带检查的 STL 实现（第83条）

  • 使用正确的 STL 查找算法（第85条）
  • 使用正确的 STL 排序算法（第86条）
  • 使谓词成为纯函数（第87条）
  • 算法和比较器的参数应多用函数对象少用函数（第88条）
  • 正确编写函数对象（第89条）
  • 避免使用类型分支，多使用多态（第90条）
  • 依赖类型，而非其表示方式（第91条）
  • 避免使用 reinterpret_cast（第92条）
  • 避免对指针使用 static_cast（第93条）
